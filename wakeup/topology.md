# topology

Architecture: Infineon TC377 + TLF35584 + TJA1145

## TJA1145

### 1. INH/WAKE

TJA1145 的 **WAKE** 引脚和 **INH** 引脚是它实现“把系统叫醒”功能的核心输出，它们在硬件设计上通常分别连接 **TLF35584（SBC）** 和 **TC377（MCU）**。

不过，这里需要先澄清一个小细节：TJA1145 作为收发器，它通常**不会直接去唤醒 TC377**，而是通过控制 SBC（TLF35584）的供电，或者仅仅作为一个唤醒状态指示给 MCU 看。

  - **INH 引脚**：TJA1145 的**输出**，作用是**把 TLF35584 叫醒（给系统供电）**。
  - **WAKE 引脚**：TJA1145 的**输入**（或状态标志），作用是**检测板内硬线信号，或者向 MCU 报告本地唤醒事件**。

以下是标准的硬件连接拓扑和这两个引脚的具体作用：

#### 1.1 INH 引脚（Inhibit Output，抑制输出/高压驱动引脚）

**作用**：这是 TJA1145 的**“大力士”引脚**。它是一个高压（12V）推挽输出，用于直接控制电源芯片（SBC）的使能或唤醒。

- **连接对象**：通常连接到 **TLF35584 的 WAK（Wake）引脚** 或 **ENA（Enable）引脚**。
- **工作逻辑**：
  - **休眠时**：INH 为低电平（或悬空）。此时 TLF35584 的 WAK 没收到高电平，保持休眠，不给 MCU 供电。
  - **唤醒瞬间**：TJA1145 检测到总线唤醒报文（或 WAKE 引脚有本地唤醒信号）。此时 TJA1145 内部从 VBAT 取电，**将 INH 拉高到 12V**。
  - **结果**：TLF35584 的 WAK 引脚检测到上升沿/高电平，TLF35584 被激活，打开内部的 BUCK/LDO，输出 3.3V/5V 给 TC377 和 TJA1145 的 VCC 引脚。
- **总结**：**INH 控制 SBC 的硬件电源开关。**

#### 1.2 WAKE 引脚（Local Wake-up Input，本地唤醒输入）

**作用**：这是 TJA1145 的**“耳朵”**。它是一个**输入**引脚（部分型号支持双向/输出标志），用于检测板内的硬线唤醒信号（例如 KL15 点火信号、门锁信号、或者其他非 CAN 的唤醒源）。

- **连接对象**：通常连接到 **板内的硬线信号**（比如点火开关 KL15），或者连接到 **TLF35584 的某个输出/状态引脚**，或者连接到 **TC377 的一个 GPIO**（视具体设计而定）。
- **工作逻辑**：
  - **输入功能（最常见）**：假设你要支持“点火信号唤醒”。硬件上，点火信号（12V）通过分压/二极管接到 TJA1145 的 WAKE 引脚。
  - 当驾驶员拧钥匙点火时，WAKE 引脚检测到电平变化（例如上升沿或持续高电平）。
  - TJA1145 收到这个本地唤醒信号后，**执行和 CAN 唤醒一样的动作**：拉高 INH -> 唤醒 TLF35584 -> 给 MCU 供电。
  - **输出/标志功能（较少见或复用）**：有些设计里，MCU 醒来后需要知道“是谁叫醒了我”。TJA1145 的 WAKE 引脚在某些模式下可以配置为输出一个唤醒事件标志（高电平），接到 TC377 的某个 GPIO（带有唤醒中断能力的引脚）。
- **总结**：**WAKE 负责监听板内硬线信号，或者告知 MCU 唤醒源。** 它不直接驱动电源，是 INH 的“触发器”之一。

#### 1.3 为什么 WAKE 引脚有时也接 TC377？

在一些特殊设计中，TJA1145 的 WAKE 引脚会有如下接法：

1. **TJA1145.WAKE 接 TC377.GPIO**：
   - 目的：MCU 醒着的时候，通过 GPIO 主动告诉 TJA1145：“我要睡了，请把 CAN 唤醒功能关掉，只保留 WAKE 引脚的硬线唤醒”。或者 MCU 利用这个引脚作为 TJA1145 中断输入，快速响应本地唤醒事件（而不通过 SPI 查询）。
2. **TJA1145.WAKE 接 TLF35584.INT**：
   
   - 目的：当 MCU 还没起来时，TLF35584 可以通过 INT 引脚的状态了解外部唤醒源，从而决定是否给 MCU 供电。

#### 1.4 如果 KL15 直接接 35584（或直接控制电源），TJA1145 的 WAKE 如何处理？

在这种架构下，TJA1145 只负责 CAN 唤醒，不负责硬线唤醒。那么 WAKE 引脚必须**终结**（不能悬空，悬空会导致引脚电平不确定，容易受干扰导致误唤醒或漏电流）。

##### 情况 A：固定下拉（接地）

- **状态**：WAKE = 0（低电平）。
- **硬件表现**：TJA1145 认为本地唤醒源一直没有发生。
- **软件配置**：MCU 在休眠前，通过 SPI 配置 TJA1145 进入 Sleep 模式时，需要**将本地唤醒检测（Local Wake-up）禁用**（或者配置为仅 CAN 唤醒）。
- **问题**：**没有任何问题。** 这是最常见的做法。此时 WAKE 引脚电平稳定，不会产生误触发。
- **注意**：如果软件没有禁用本地唤醒，且在 TJA1145 进入 Sleep 前，如果引脚电平从高变低（比如之前配置过内部上拉，现在外部强制下拉），**有可能触发一次虚假的本地唤醒**。因此，下电时序上要保证先配寄存器、清标志，再进 Sleep。

##### 情况 B：固定上拉（接 12V 常电或 VCC）

- **状态**：WAKE = 1（高电平）。
- **硬件表现**：TJA1145 认为“本地唤醒源一直有效”。
- **问题**：**存在一个严重的功能陷阱。** 如果 TJA1145 的寄存器中使能了本地唤醒功能（LWU Enable），且 WAKE 引脚一直为高电平，那么芯片会认为一直有唤醒请求。
  - **结果**：当你命令 TJA1145 进入 Sleep 时，它**可能拒绝进入深度睡眠**，或者进去后**立刻被 WAKE 高电平唤醒**，导致 INH 被拉高，SBC 重新给 MCU 供电，系统无法休眠。
- **解决方案**：如果你确实因为某些原因（比如该引脚耐压高，方便布线）想接上拉，那么软件在进入睡眠前，**必须通过 SPI 把 Local Wake-up 检测功能彻底禁用**，让 TJA1145 忽略 WAKE 引脚的电平。

**结论**：**推荐固定下拉。** 如果接上拉，硬件上不坏，但软件必须记得关掉本地唤醒检测，否则系统无法正常休眠。



#### 1.5 架构对比：KL15 接哪里更合理？

在真实的 ECU 设计中，**把 KL15 同时给 35584 和 TJA1145（或者只给 35584）都是可行的**，但逻辑上有些许区别：

##### 方案一：KL15 只接 35584（TJA1145 WAKE 下拉）

- **唤醒路径**：拧钥匙 -> 35584 被硬线唤醒 -> 35584 直接给 MCU 和 TJA1145 供电。
- **优点**：路径短，即使 CAN 收发器坏了，或者 TJA1145 死机了，只要 35584 是好的，MCU 就能被唤醒（这对于诊断或安全功能很重要）。
- **TJA1145 状态**：TJA1145 此时是被动上电（VCC 来电了），它不需要依靠 WAKE 引脚，也不需要拉高 INH。

##### 方案二：KL15 接 TJA1145 的 WAKE（TJA1145 INH 接 35584 WAK）

- **唤醒路径**：拧钥匙 -> TJA1145 检测到 WAKE 高电平 -> TJA1145 拉高 INH -> 35584 被 INH 唤醒 -> 供电。
- **优点**：TJA1145 可以在硬件层面记录“这次醒来是因为 KL15”，MCU 醒来后读 SPI 寄存器就能区分“点火唤醒”和“CAN 唤醒”。
- **缺点**：唤醒路径依赖 TJA1145。如果 TJA1145 损坏，或者 SPI 配置把 WAKE 引脚禁用了，即使拧了钥匙，MCU 也起不来。这在某些安全等级要求高的 ECU 上是不被允许的。

##### 总结建议

针对“如果不接 KL15，直接硬件下拉或上拉会不会有问题”：

1. **接下拉（GND）**：**完全没问题，放心用。** 这是标准做法，只要 TJA1145 的 VCC 脚由 SBC 供电即可。
2. **接上拉（VBAT/VCC）**：**电气上没问题，但逻辑上是个坑。** 必须在软件配置里**关闭 Local Wake-up 功能**，否则会导致系统无法进入休眠或反复重启。

**工程建议**：在量产硬件设计中，即使你现在不用 KL15 唤醒 TJA1145，**也建议在 WAKE 引脚和 KL15 之间预留一个 0 欧电阻或二极管的位置**，并保留一个下拉电阻的位置。这样，如果以后发现需要通过 TJA1145 区分 KL15 唤醒源，硬件不用改版，只需要调整焊接即可。

#### 1.6 假设项目只需要kl15唤醒，那kl15直接接到电源芯片的唤醒引脚不就好了，把1145的INH引脚下拉掉

**在“仅需 KL15 硬线唤醒”的项目中，TJA1145 的 INH 引脚完全可以不接电源芯片，直接下拉处理，整个系统也能正常工作。**

**INH 是否必须接电源芯片，取决于 TJA1145 是否承担唤醒任务。**

- **承担任务（支持 CAN 远程唤醒）**：INH 必须接 35584，否则无法把系统从无电状态拉起来。
- **不承担任务（仅 KL15 本地唤醒）**：INH 就是个多余的高压输出脚，直接下拉或悬空（按手册建议）即可。此时 TJA1145 就是一颗**带 SPI 诊断功能的普通 CAN 收发器**，和 TJA1043 在单纯通信场景下的用法差不多。

##### 1.6.1 为什么可以不用 INH？

TJA1145 的 INH 引脚存在的唯一目的，就是**在芯片没有 VCC 供电（即 SBC 休眠）时，依靠 VBAT 常电，通过拉高 INH 去“指挥”电源芯片给系统上电**。

如果项目的唤醒源只有 KL15：

- **KL15 直接接 35584**：拧钥匙 -> 35584 直接被硬线叫醒 -> 35584 开始输出 VCC。
- **TJA1145 的角色变了**：它不再负责“唤醒系统”，而是变成了一个**纯粹的被供电设备**。VCC 来了它就工作，VCC 没了它就睡觉。
- **既然 TJA1145 不需要主动去叫醒谁，INH 引脚自然就失去了作用。** 一颗不用的输出引脚，直接做下拉（或悬空，视芯片手册要求，通常建议下拉）终结即可。

##### 1.6.2 系统上电时序会变成什么样？

在纯 KL15 方案下，时序变得非常简单粗暴：

1. **初始**：整车休眠，35584 关闭，VCC=0，MCU 没电，TJA1145 也没电（但 VBAT 有常电供着内部低功耗监听电路，如果 CAN 唤醒没关，它其实还在“偷听”总线，但偷听到了也起不了作用，因为 INH 没接）。
2. **点火**：KL15 拉高 -> 35584 的 WAK/EN 引脚收到高电平。
3. **供电**：35584 打开，VCC 输出 5V/3.3V。
4. **启动**：MCU 上电复位，TJA1145 的 VCC 上电。
5. **初始化**：MCU 跑代码，通过 SPI 把 TJA1145 配置为 Normal 模式，开始正常的 CAN 通信。

##### 1.6.3 需要注意的“坑”（工程细节）

虽然逻辑成立，但在硬件设计和软件配置上，有几个点必须处理好，否则会有隐患：

###### 坑 1：TJA1145 的“惯性”唤醒（CAN 误唤醒导致漏电）

- **现象**：虽然你 INH 没接 35584，但如果 TJA1145 的 CAN 唤醒功能（CWE）没关，当总线上有垃圾报文时，TJA1145 内部检测到总线活动，**它依然会尝试把 INH 拉高**（只不过这个高电平没接到 SBC，所以 35584 不会上电，MCU 不会醒）。
- **后果**：INH 引脚在做无用功，同时 TJA1145 内部的唤醒标志位被置位，芯片内部状态变了。
- **影响**：下次 KL15 唤醒 MCU 后，MCU 读 TJA1145 状态寄存器时，可能会误以为“上次系统醒来是因为 CAN 唤醒”，导致软件逻辑判断出错。
- **对策**：MCU 在每次休眠前（关闭 35584 之前），或者每次启动初始化时，通过 SPI **清除 TJA1145 的唤醒标志，并且最好直接禁用 CAN 唤醒功能**。

###### 坑 2：进入休眠时的时序

- 当你关闭 KL15 时，35584 断电，VCC 消失。TJA1145 会瞬间掉电。
- 这通常没问题，因为 TJA1145 允许 VCC 直接掉电（回到 Standby/Sleep 状态）。
- 但为了保护 TJA1145 的内部逻辑，最好在 MCU 检测到 KL15 关闭后，先通过 SPI 给 TJA1145 发送一个 **Go to Sleep 命令**，把模式切到 Sleep，再让 35584 断电。这样下一次上电时，TJA1145 的状态是明确的。

###### 坑 3：KL15 的抗扰与分压

- KL15 是整车级别的硬线，上面会有各种干扰脉冲（抛负载、负脉冲等）。
- 接 35584 的唤醒引脚时，需要做合适的**分压、限流、TVS 保护和 RC 滤波**，确保 35584 不会被误触发或损坏。

#### 1.7 mcu如何识别唤醒源呢？假设项目同时支持kl15、特定帧应用报文、nm报文三种唤醒。硬件上如何连接，才能保证软件能读到真正的唤醒源是谁

##### 1.7.1 硬件连接方案

为了能让 MCU 区分三种唤醒源，硬件的核心原则是：**让不同的唤醒源在硬件上留下不同的“痕迹”，且 MCU 醒来后能够通过 GPIO 或 SPI 读取到这些痕迹。**

推荐方案：唤醒源分流 + 状态寄存器 + GPIO 直连。

1. **KL15 vs CAN 唤醒**：靠 **GPIO 直读 KL15 电平** 或 **TJA1145.WAKE 引脚状态** 区分，硬件层面就能解决。
2. **特定帧 vs NM 报文**：**硬件无法区分**，必须靠 MCU 在 **Listen-Only 模式下被动接收第一帧报文** 来判断。这是 AUTOSAR CanNm 和 CanIf 的标准做法。
3. **硬件设计核心**：**KL15 分压后直连 MCU GPIO** + **TJA1145 和 35584 都保留 SPI/中断接口**，这样 MCU 醒来后能最快、最准地完成唤醒源识别。

| 信号                       | 连接方式                                                  | 作用                                                         |
| -------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| KL15                       | 同时接到 **35584.WAK** 和 **TJA1145.WAKE**（或只接35584） | 让两处都能留下 KL15 的“指纹”                                 |
| 35584.INT                  | 接到 **TC377 的 GPIO**（带中断功能）                      | MCU 醒来后快速查询 35584 的唤醒源                            |
| TJA1145.SPI                | 接到 TC377 的 SPI                                         | MCU 通过 SPI 读取 TJA1145 的事件寄存器，获取 CAN 唤醒标志    |
| TJA1145.INH                | 接到 35584.WAK（**可选但推荐**）                          | 让 TJA1145 也能唤醒 35584，同时 35584 能记录“被 INH 唤醒”这一事件 |
| KL15 分压后直连 TC377.GPIO | 通过分压电阻 + 二极管接到一个 GPIO                        | **最直接的 KL15 状态读取**，MCU 醒来后第一眼就能看到 KL15 是高还是低 |

##### 1.7.2 三种唤醒源的“痕迹”矩阵

MCU 醒来后，通过读取不同的硬件状态，可以构建一个**唤醒源判定矩阵**：

| 唤醒源             | 35584.WAK 是否被触发 | TJA1145.WAKE 是否被触发 | TJA1145.CAN唤醒标志 | KL15 GPIO 电平 |
| ------------------ | -------------------- | ----------------------- | ------------------- | -------------- |
| **KL15 硬线**      | ✅                    | ✅（如果接了）           | ❌                   | **高**         |
| **特定帧应用报文** | ✅（被 INH 唤醒）     | ❌                       | ✅（标准WUP触发）    | 低             |
| **NM 报文**        | ✅（被 INH 唤醒）     | ❌                       | ✅（标准WUP触发）    | 低             |

**关键洞察**：

- **KL15 vs CAN 唤醒**：通过 KL15 GPIO 电平或 TJA1145.WAKE 标志就能直接区分。
- **特定帧 vs NM 报文**：**硬件上无法直接区分！** 因为两者都是 CAN 总线活动触发的。区分这两者必须依靠 **MCU 软件层面的唤醒验证（Wakeup Validation）**。

##### 1.7.3 软件识别唤醒源的完整流程

###### 第 1 步：MCU 上电，进入 Startup

MCU 从复位向量开始执行，EcuM_Init 被调用。

###### 第 2 步：快速读取硬件“痕迹”（在 CAN 初始化之前）

MCU 在 **EcuM_Init 或 EcuM_StartWakeupValidation** 阶段，**立即执行以下动作**（此时 CAN 控制器还未完全打开，总线还没有任何发送行为）：

```c
/* 1. 读取 KL15 GPIO（最快、最直接） */
boolean kl15Active = Dio_ReadChannel(KL15_GPIO_CHANNEL);

/* 2. 通过 SPI 读取 TJA1145 的事件寄存器 */
uint8 tja1145_event = CanTrcv_ReadEventStatus(&tja1145_cfg);
boolean canWakeupFlag = (tja1145_event & TJA1145_EVENT_CAN_WAKEUP) ? TRUE : FALSE;
boolean localWakeupFlag = (tja1145_event & TJA1145_EVENT_LOCAL_WAKEUP) ? TRUE : FALSE;

/* 3. 读取 35584 的中断/状态寄存器（可选） */
uint8 sbc_status = Sbc_ReadStatus(&sbc_cfg);
boolean sbcWakPinTriggered = (sbc_status & SBC_STATUS_WAK) ? TRUE : FALSE;
```

###### 第 3 步：初步判定唤醒源类别

```c
if (kl15Active || localWakeupFlag) {
    // 唤醒源 = KL15 硬线
    wakeupSource = WAKEUP_KL15;
    // 走 KL15 唤醒流程：直接进入正常通信，不需要 CAN 唤醒验证
    EcuM_SetWakeupSource(WAKEUP_KL15);
} else if (canWakeupFlag) {
    // 唤醒源 = CAN 总线（可能是特定帧，也可能是 NM 报文）
    wakeupSource = WAKEUP_CAN;
    // 进入 CAN 唤醒验证流程
    EcuM_SetWakeupSource(WAKEUP_CAN);
    // 启动 CanNm 的被动监听模式，开始验证
} else {
    // 未知唤醒源，可能是干扰，直接进入休眠准备
    wakeupSource = WAKEUP_UNKNOWN;
}
```

###### 第 4 步：CAN 唤醒的进一步验证（区分特定帧 vs NM 报文）

如果是 CAN 唤醒，MCU **进入静默监听模式**（CAN 控制器配置为 Listen-Only，不发送任何报文，不发送 ACK）：

```c
// 配置 MCMCAN 为 Listen-Only 模式
CanIf_SetControllerMode(CANIF_CTRL_MODE_LOM);

// 启动一个验证定时器
EcuM_StartWakeupValidationTimer(CAN_WAKEUP_VALIDATION_TIMEOUT);
```



**验证逻辑**：

- **接收第一帧报文**：MCU 被动接收 CAN 总线上到达的报文。
- **判断报文类型**：
  - 如果收到的第一帧是 **NM 报文**（ID 匹配 CanNm 配置的 NM Tx/Rx ID），则 `wakeupSource = WAKEUP_CAN_NM`。
  - 如果收到的第一帧是 **特定应用唤醒帧**（ID/Data 匹配应用层定义的唤醒帧，比如诊断唤醒帧 0x7DF），则 `wakeupSource = WAKEUP_CAN_APP`。
  - 如果收到的第一帧都不是，继续等待。
- **超时处理**：
  - 如果在超时时间内收到了合法的唤醒帧（NM 或 APP），验证通过，ECU 进入正常通信模式。
  - 如果超时未收到合法帧，验证失败，ECU 进入休眠准备流程。

##### 1.7.4 更精确的硬件方案：让 KL15 直接能被 MCU 看到

为了让 KL15 唤醒源的识别**最快、最可靠**，硬件设计上通常会做以下处理：KL15 分压后直连 TC377 的 GPIO

```
KL15 (12V) ----/\/\/\----+----/\/\/\---- GND
              R1=47k     |
                         +----> TC377.GPIO (例如 P02.0)
                         |
                        ---  C=100nF (去抖)
                        ---
                         |
                        GND
```

- **为什么这样做**：MCU 上电后，**无需等待 SPI 通信完成**，只需读一个 GPIO 电平就能立即知道 KL15 是否有效。这比读 TJA1145 或 35584 的寄存器快得多。
- **工程细节**：需要加 TVS 管保护，防止 KL15 上的负脉冲或抛负载损坏 MCU 引脚。
