# Q&A

Architecture: Infineon TC377 + TLF35584 + TJA1145

## 1 单板第一次12V上电时，没有唤醒信号，此时35584应该都在未初始化或休眠态，1145、377应该都处于未上电状态，因为sbc还没有对外输出3.3v或5v供电。sbc收到外部的硬线信号被唤醒，或通过can唤醒1145来间接唤醒sbc，这两种方式让sbc进入工作态并对外输出供电。此时377进入初始化流程。但是不是有个矛盾点：1145还没有经sbc供电，它收到can唤醒信号后，如何通过inh引脚对外输出，来唤醒sbc呢？

TJA1145 在设计上就是为了解决“系统主电源断电时如何被总线唤醒”这个问题的。它的秘诀依然在于**双电源架构**。

### 1.1 核心：TJA1145 的“常电”引脚（VBAT）

TJA1145 通常有这几个电源引脚：

- **VBAT**：**电池常电引脚**。在硬件设计时，这个引脚**直接连接 12V 蓄电池**，不经过 35584（SBC）的控制。
- **VCC**：**逻辑供电引脚**。这个引脚接 35584 输出的 5V 或 3.3V，用于正常通信。
- **VIO**：数字接口电平参考（接 MCU 的 IO 电平）。

**关键机制**：只要 12V 蓄电池还连着 ECU，**VBAT 引脚就始终有电**。此时，即使 VCC 完全没有电（即 35584 处于休眠、未对外输出），TJA1145 内部的一个**极低功耗的“总线唤醒接收器”**依然处于待命状态。

### 1.2 解决矛盾：没有 VCC，INH 怎么输出高电平？

你可能会疑惑：芯片主逻辑没供电（VCC=0），它怎么有力气把 INH 拉高呢？

**答案**：TJA1145 的 INH 引脚是**高压引脚**，它的驱动能量直接来源于 **VBAT（12V 常电）**，而不是 VCC。

TJA1145 数据手册中关于 INH 的描述明确指出：**INH 引脚是一个高压输出引脚，内部通过一个高边开关连接到 VBAT**。

唤醒流程如下：

1. **监听**：TJA1145 由 VBAT 供电的微弱监听电路一直在线。
2. **识别**：CAN 总线上出现符合 ISO 11898 标准的唤醒报文（Wake-up Pattern）。
3. **动作**：TJA1145 内部逻辑被触发，**打开 VBAT 到 INH 的开关**。
4. **输出**：INH 引脚直接输出 VBAT 电压（通常是 12V 或电池电压）。
5. **唤醒 SBC**：这个 12V 的 INH 信号传到 35584 的唤醒输入引脚（如 WK 或 EN），35584 被激活，开始输出 3.3V/5V 给 MCU 和 TJA1145 的 VCC。

### 1.3 三种场景的完整状态流转

#### 场景 A：单板第一次接 12V 常电（无任何唤醒信号）

- **状态**：35584 处于**未初始化或休眠态**，不输出 3.3V/5V。
- **TJA1145**：**VCC=0，但 VBAT=12V**。TJA1145 进入 **Standby（待机）或 Sleep（睡眠）模式**（具体模式取决于硬件上电默认配置和软件是否曾经配过）。此时它的 INH 是**悬空或拉低**的（取决于模式，但不会主动输出高电平去打开 35584）。
- **结果**：MCU（377）和驱动芯片没电，单板处于静默状态，只有极低的静态电流（TJA1145 监听 + SBC 休眠）。

#### 场景 B：硬线直接唤醒 SBC

- **动作**：外部点火信号（IGN）或硬线信号直接输入到 35584 的唤醒引脚。
- **过程**：35584 被硬线电平触发，**直接**开始上电，输出 3.3V/5V。
- **TJA1145**：VCC 得电，TJA1145 进入正常模式。
- **377**：得电启动。

#### 场景 C：通过 CAN 唤醒 TJA1145，间接唤醒 SBC

- **初始**：单板处于休眠状态（35584 关断，VCC=0），但 12V 常电在线（VBAT=12V）。
- **动作**：外部 ECU 在 CAN 总线上发唤醒报文。
- **过程**：TJA1145 的低功耗接收器检测到唤醒（**注意：此时 35584 仍未工作**） -> TJA1145 的 INH 由 **VBAT 驱动**输出高电平 -> 35584 检测到 INH 高电平 -> 35584 打开主电源 -> 377 启动。

## 2 场景C中的Wake-up Pattern需要提前配置在1145里吗？假设需要支持网络管理报文唤醒呢？或是特定帧唤醒？或是任意帧唤醒？1145能配置成同时支持网络管理报文唤醒和特定应用报文帧唤醒吗？要如何配置1145，377是不是也需要在软件里匹配配置？

**Wake-up Pattern（唤醒模式）不需要提前把“具体数据”配置进去，但需要提前通过 SPI 配置 TJA1145 的“唤醒判定规则寄存器”。**

### 2.1 Wake-up Pattern 到底是什么？
在 TJA1145 的硬件机制中，它所谓的“Wake-up Pattern”**不是**指具体的一帧数据（比如 ID=0x123, Data=0xAA），而是指 **CAN 总线上的物理电平特征**。

根据 ISO 11898-6（唤醒规范）和 TJA1145 数据手册，标准的 CAN 唤醒模式（Standard Wake-up Pattern, WUP）定义如下：

- 在总线上监测到一个 **显性（Dominant）电平**（持续至少 $t_{filter}$时间，通常是几百纳秒到几微秒）。
- 随后跟着一个 **隐性（Recessive）电平**（持续至少 $t_{filter}$ 时间）。
- 如此交替出现 **至少 2 次**（具体次数可配置）。

**结论**：只要总线上有任意 CAN 控制器在发送数据（无论是 NM 报文、应用报文还是错误帧），总线上就会出现显性-隐性交替的电平。因此，**硬件唤醒机制本身不区分 ID 或数据内容**。

### 2.2 网络管理报文唤醒、特定帧唤醒、任意帧唤醒
在实际 ECU 开发中，这三种唤醒在软硬件分工上完全不同：

#### 2.2.1 任意帧/任意总线活动唤醒（最简单，功耗较高）
- **TJA1145 配置**：使能 CAN Wake-up 功能（`CWE=1`），配置标准 WUP。
- **现象**：总线上只要有任何风吹草动（哪怕是一个错误帧），TJA1145 就会拉高 INH，唤醒 SBC 和 MCU。
- **优点**：不会漏唤醒。
- **缺点**：总线干扰可能导致 ECU 被频繁误唤醒，不符合低功耗要求。

#### 2.2.2 特定帧唤醒 / 网络管理报文唤醒（进阶，AUTOSAR 标准做法）
**关键点：在绝大多数量产项目中，硬件不负责区分具体报文，只负责“叫醒”，具体区分交给 MCU 软件。**

- **TJA1145 配置**：依然是配置标准的 WUP（显隐性交替）。TJA1145 本身**无法**配置成只响应 ID=0x500 的 NM 报文而忽略 ID=0x123 的应用报文（除非使用 TJA1145 的 Partial Networking 功能，见下文）。

- **工作流程（软硬件结合）**：

  ##### 第 1 步：硬件唤醒，MCU 上电

  - CAN 总线上出现任意报文（可能是 NM，可能是应用报文，甚至是干扰）。
  - TJA1145 检测到总线活动 -> INH 拉高 -> SBC 上电 -> TC377 上电复位。

  ##### 第 2 步：EcuM 确认唤醒源（仅读状态，不碰总线）

  - MCU 开始跑启动代码。
  - EcuM（ECU State Manager）启动，通过 SPI 读取 TJA1145 的事件寄存器。
  - 得出结论：“哦，是 CAN 总线唤醒了我”。
  - 但是，ECU 目前处于 **Startup 状态**，网络状态机是 **COMM_NO_COMMUNICATION**（禁止通信）。

  ##### 第 3 步：进入 CAN 侦听/验证状态（Listening / Passive）

  此时，MCU **打开 CAN 控制器的接收功能，但严格保持发送静默（不发送任何报文）**。

  - **硬件配置**：TC377 的 MCMCAN 控制器被初始化。
    - **收发器（TJA1145）**：通过 SPI 将 TJA1145 从 Standby 模式切换到 **Normal 模式**，但 TJA1145 的 TXD 引脚保持拉高（隐性）。收发器可以接收，但即使 MCU 不发送，总线也不会因为 MCU 而动作（相当于接收器在线）。
    - **CAN 控制器**：MCMCAN 设置为**不发送 ACK（Self Reception / Silent Mode，静默模式）**，或者仅仅开启接收中断，**完全关闭发送 API**。
  - **网络管理（CanNm）动作**：
    - CanNm 进入 **Network Mode 的 Repeat Message State 或立刻进入 Listen 模式**。
    - CanNm 开始**监听总线上的数据**。

  ##### 第 4 步：唤醒验证（Wakeup Validation）

  - CanNm 会设置一个定时器（通常叫 `CanNmTimeoutTime` 或 `CanNmWaitBusSleepTime`）。
  - **情况 A：收到预期报文（如有效的 NM 报文）**
    - CanNm 确认收到合法的 NM 报文（或者应用层指定的特定唤醒帧）。
    - **验证成功**。
    - CanNm 通知 EcuM：“验证通过，请给我供电，我要开始通信了”。
    - EcuM 执行 `ComM_Nm_NetworkMode`，网络状态切换为 `COMM_FULL_COMMUNICATION`。
    - **此时，CAN 控制器才被允许发送 ACK 和发送报文。** ECU 正式加入总线，给外部 ECU 发出“我醒了”的信号。
  - **情况 B：超时未收到合法报文（收到的是干扰或无关应用帧）**
    - CanNm 告知 EcuM：“验证失败，这是虚假唤醒”。
    - EcuM 关闭 CAN 控制器，通过 SPI 把 TJA1145 重新设置为 Sleep 模式。
    - SBC 关闭电源，ECU 重新回到休眠状态。
    - 全程 MCU 没有向外发送过任何错误帧、ACK 或应用报文。

#### 2.2.3 TJA1145 的 Partial Networking（特定帧硬件唤醒）

如果你希望在硬件层面就过滤掉非唤醒帧，TJA1145 系列（特别是 TJA1145A/FD 或 TJA1145B）支持 **Partial Networking（局部网络，ISO 11898-6）**。

- **原理**：TJA1145 内部集成了一个简单的 CAN 协议解析器（不仅看物理电平，还看数据链路层）。
- **配置方式**：通过 SPI，你可以提前向 TJA1145 写入一组 **唤醒帧配置寄存器（WUFC，Wake-up Frame Control）**。
  - 你需要指定 **CAN ID**（例如 NM 报文的 ID=0x500）。
  - 你需要指定 **数据掩码（Data Mask）**（例如只关心 Byte0 的 bit0）。
  - 你需要指定 **数据内容（Data Value）**。
- **效果**：只有总线上出现与你配置的 ID 和 Data 完全匹配的报文时，TJA1145 才会拉高 INH。如果总线上是其他应用报文，TJA1145 保持沉默，SBC 继续睡觉。
- **代价**：配置复杂，需要计算 CRC，且**只能配置有限的几组**（通常是 1 到 4 组唤醒帧）。

### 2.3 TJA1145 能否同时支持 NM 报文和特定应用报文唤醒？

**如果使用 Partial Networking 功能：**
可以**部分支持**。TJA1145 通常有多组唤醒寄存器（例如支持配置 4 个不同的唤醒 ID）。你可以：

- **槽位 0**：配置成 NM 报文的 ID（如 0x500）。
- **槽位 1**：配置成特定的应用诊断唤醒报文 ID（如 0x7DF）。
- 只要满足其一，即可唤醒。

**如果不使用 Partial Networking（即常规配置）：**
它**同时也支持**所有的报文。因为它工作在物理层，不管是 NM 报文还是应用报文，只要总线有电平翻转它就醒。区别只在于 MCU 醒来后软件是否认账。

### 2.4 如何配置 TJA1145？TC377 需要怎么配合？

为了实现在验证阶段的“监听且静默”，TJA1145 和 TC377 的配置如下：

**TJA1145（通过 SPI 配置）：**

1. 唤醒后，MCU 首先读 TJA1145 的事件寄存器，确认是 CAN 唤醒。
2. 将 TJA1145 从 **Standby** 切到 **Normal** 模式。
3. **关键点**：为了监听总线，TJA1145 的接收器是开启的。但此时 TJA1145 的 TXD（发送数据输入）引脚被 MCU 拉高（隐性）。**只要 MCU 不拉低 TXD，TJA1145 就不会驱动总线为显性，也不会发出 ACK**。

**TC377（MCMCAN 配置）：**

1. **初始化阶段**：MCMCAN 设置为 `CAN_CTRL_MODE_LOM`（Listen Only Mode，只听模式）或 `MON`（Monitor）。
2. **在 Listen Only 模式下**：
   - 可以收到总线上的报文。
   - **硬件上自动禁止发送 ACK/错误帧/数据帧**。
3. **验证通过后**：
   - ComM 请求 `CanIf_SetControllerMode(CANTRCV_OPMODE_NORMAL)`。
   - MCMCAN 退出 Listen Only，进入 Normal 模式，此时才能正常发报文和 ACK。

## 3 超时未收到合法报文，重新进入休眠，因为此时总线上还有无效报文（非唤醒应用报文帧或非唤醒nm报文），那岂不是立马又会唤醒1145，再次把sbc唤醒，有一次进入判定，然后再次休眠，循环往复，这是可接受的吗？
**这完全不可接受，必须通过软件和硬件机制来打破这个循环。**

### 3.1 第一道防线：TJA1145 的“唤醒锁存”机制
TJA1145 内部有一个唤醒事件锁存器。

- **关键特性**：当总线活动触发唤醒后，TJA1145 会**锁存（Latch）**这个唤醒事件，并且**自动关闭/屏蔽后续的唤醒检测**（或者说唤醒标志位被置位后，不会因为总线还在活动而反复触发硬件复位动作）。
- **流程表现**：只要 MCU 还没通过 SPI 去**清除唤醒标志（Clear Wake-up Flag）**，TJA1145 就不会再次因为总线上的无效报文去拉高 INH。
- **问题场景**：MCU 被无效报文唤醒 -> MCU 进入验证 -> 验证失败 -> MCU 下发“进入休眠”命令 -> **在执行休眠命令前，MCU 会先清除 TJA1145 的唤醒标志** -> 然后发送 Sleep 命令。
- **结果**：只有当唤醒标志被清除并进入 Sleep 后，TJA1145 才会重新武装（Re-arm）唤醒检测功能。

### 3.2 第二道防线：MCU 软件（EcuM/CanNm）的“休眠屏蔽”策略

如果总线上的无效报文是**持续不断**的（比如总线上其他节点在疯狂发应用报文，或者总线短路导致一直有杂波），MCU 软件不能机械地“验证失败就立刻睡”。

AUTOSAR 网络管理引入了 **Bus-off / 被动等待 / 延后休眠** 的概念：

- **策略 A：提高休眠门槛（Timeout Extension）**
  软件逻辑通常是：验证失败 -> 不睡，继续听一段时间 -> 如果总线一直忙，就一直等 -> 直到**总线安静了**（比如检测到 Bus-Silent 持续 1 秒或更久），软件才认为外部环境安全了，此时才清除 TJA1145 标志并命令休眠。
- **策略 B：软件屏蔽唤醒源**
  如果软件发现“导致我醒来的这个源是个捣蛋鬼”，MCU 可以在本次休眠前，**通过 SPI 修改 TJA1145 的寄存器配置**。
  - 比如：关闭 CAN 总线唤醒（Disable CAN Wake-up），只保留硬线唤醒。
  - 或者：配置成 Partial Networking（局部网络），让 TJA1145 在硬件层面就过滤掉那个“非唤醒应用报文”，只对特定的 NM 报文敏感。
  - 这样，即使总线上还有无效报文，TJA1145 在硬件上就无视它了，不会产生中断，也不会拉高 INH。

### 3.3 第三道防线：物理层的“总线静默”假设

在正常的车载网络设计中，**网络管理（NM）的核心逻辑就是“大家一起睡，一起醒”**。

- **正常场景**：所有 ECU 要休眠时，它们会先协调好。最后休眠的 ECU 会停止发送 NM 报文。一旦所有 ECU 都停止发送 NM 报文，**整条 CAN 总线就处于“总线静默（Bus Silent）”状态**（只有纯隐性电平，没有任何报文）。
- **无效报文场景**：如果总线上还有应用报文在飞，说明**还有 ECU 在工作**（比如娱乐系统还在放歌，或者某个节点还没准备睡）。
- **设计策略**：如果你的 ECU 不需要参与当前的通信（比如变速箱不需要娱乐系统的报文），但又因为娱乐系统的报文被吵醒了，**软件通常会选择“陪跑”**。即：既然总线上还有系统在工作，说明整车还没到完全休眠的时候，那变速箱 ECU 索性也保持唤醒（或者进入一个低功耗的“听但不发”状态），**等到总线彻底静默了，再执行休眠**。

### 3.4 极端的异常处理：连续唤醒计数

如果发生极端情况（例如总线对地短路导致持续显性，或者某个节点程序跑飞疯狂发错误帧），MCU 软件通常会有一个**计数器**。

- 逻辑：如果我在短时间内（如 10 秒内）被连续唤醒超过了 N 次（如 5 次）。
- 动作：MCU 会判定“硬件可能存在故障”。
- 结果：MCU 可能直接命令 SBC 进入 **Fail-Safe 模式**，或者**彻底关闭 TJA1145 的 CAN 唤醒功能**，只保留硬线（KL15）唤醒，以防止电池电量被耗尽。

## 4 INH/WAKE

TJA1145 的 **WAKE** 引脚和 **INH** 引脚是它实现“把系统叫醒”功能的核心输出，它们在硬件设计上通常分别连接 **TLF35584（SBC）** 和 **TC377（MCU）**。

不过，这里需要先澄清一个小细节：TJA1145 作为收发器，它通常**不会直接去唤醒 TC377**，而是通过控制 SBC（TLF35584）的供电，或者仅仅作为一个唤醒状态指示给 MCU 看。

  - **INH 引脚**：TJA1145 的**输出**，作用是**把 TLF35584 叫醒（给系统供电）**。
  - **WAKE 引脚**：TJA1145 的**输入**（或状态标志），作用是**检测板内硬线信号，或者向 MCU 报告本地唤醒事件**。

以下是标准的硬件连接拓扑和这两个引脚的具体作用：

### 4.1 INH 引脚（Inhibit Output，抑制输出/高压驱动引脚）

**作用**：这是 TJA1145 的**“大力士”引脚**。它是一个高压（12V）推挽输出，用于直接控制电源芯片（SBC）的使能或唤醒。

- **连接对象**：通常连接到 **TLF35584 的 WAK（Wake）引脚** 或 **ENA（Enable）引脚**。
- **工作逻辑**：
  - **休眠时**：INH 为低电平（或悬空）。此时 TLF35584 的 WAK 没收到高电平，保持休眠，不给 MCU 供电。
  - **唤醒瞬间**：TJA1145 检测到总线唤醒报文（或 WAKE 引脚有本地唤醒信号）。此时 TJA1145 内部从 VBAT 取电，**将 INH 拉高到 12V**。
  - **结果**：TLF35584 的 WAK 引脚检测到上升沿/高电平，TLF35584 被激活，打开内部的 BUCK/LDO，输出 3.3V/5V 给 TC377 和 TJA1145 的 VCC 引脚。
- **总结**：**INH 控制 SBC 的硬件电源开关。**

### 4.2 WAKE 引脚（Local Wake-up Input，本地唤醒输入）

**作用**：这是 TJA1145 的**“耳朵”**。它是一个**输入**引脚（部分型号支持双向/输出标志），用于检测板内的硬线唤醒信号（例如 KL15 点火信号、门锁信号、或者其他非 CAN 的唤醒源）。

- **连接对象**：通常连接到 **板内的硬线信号**（比如点火开关 KL15），或者连接到 **TLF35584 的某个输出/状态引脚**，或者连接到 **TC377 的一个 GPIO**（视具体设计而定）。
- **工作逻辑**：
  - **输入功能（最常见）**：假设你要支持“点火信号唤醒”。硬件上，点火信号（12V）通过分压/二极管接到 TJA1145 的 WAKE 引脚。
  - 当驾驶员拧钥匙点火时，WAKE 引脚检测到电平变化（例如上升沿或持续高电平）。
  - TJA1145 收到这个本地唤醒信号后，**执行和 CAN 唤醒一样的动作**：拉高 INH -> 唤醒 TLF35584 -> 给 MCU 供电。
  - **输出/标志功能（较少见或复用）**：有些设计里，MCU 醒来后需要知道“是谁叫醒了我”。TJA1145 的 WAKE 引脚在某些模式下可以配置为输出一个唤醒事件标志（高电平），接到 TC377 的某个 GPIO（带有唤醒中断能力的引脚）。
- **总结**：**WAKE 负责监听板内硬线信号，或者告知 MCU 唤醒源。** 它不直接驱动电源，是 INH 的“触发器”之一。

### 4.3 为什么 WAKE 引脚有时也接 TC377？

在一些特殊设计中，TJA1145 的 WAKE 引脚会有如下接法：

1. **TJA1145.WAKE 接 TC377.GPIO**：
   - 目的：MCU 醒着的时候，通过 GPIO 主动告诉 TJA1145：“我要睡了，请把 CAN 唤醒功能关掉，只保留 WAKE 引脚的硬线唤醒”。或者 MCU 利用这个引脚作为 TJA1145 中断输入，快速响应本地唤醒事件（而不通过 SPI 查询）。
2. **TJA1145.WAKE 接 TLF35584.INT**：
   
   - 目的：当 MCU 还没起来时，TLF35584 可以通过 INT 引脚的状态了解外部唤醒源，从而决定是否给 MCU 供电。

### 4.4 如果 KL15 直接接 35584（或直接控制电源），TJA1145 的 WAKE 如何处理？

在这种架构下，TJA1145 只负责 CAN 唤醒，不负责硬线唤醒。那么 WAKE 引脚必须**终结**（不能悬空，悬空会导致引脚电平不确定，容易受干扰导致误唤醒或漏电流）。

#### 情况 A：固定下拉（接地）

- **状态**：WAKE = 0（低电平）。
- **硬件表现**：TJA1145 认为本地唤醒源一直没有发生。
- **软件配置**：MCU 在休眠前，通过 SPI 配置 TJA1145 进入 Sleep 模式时，需要**将本地唤醒检测（Local Wake-up）禁用**（或者配置为仅 CAN 唤醒）。
- **问题**：**没有任何问题。** 这是最常见的做法。此时 WAKE 引脚电平稳定，不会产生误触发。
- **注意**：如果软件没有禁用本地唤醒，且在 TJA1145 进入 Sleep 前，如果引脚电平从高变低（比如之前配置过内部上拉，现在外部强制下拉），**有可能触发一次虚假的本地唤醒**。因此，下电时序上要保证先配寄存器、清标志，再进 Sleep。

#### 情况 B：固定上拉（接 12V 常电或 VCC）

- **状态**：WAKE = 1（高电平）。
- **硬件表现**：TJA1145 认为“本地唤醒源一直有效”。
- **问题**：**存在一个严重的功能陷阱。** 如果 TJA1145 的寄存器中使能了本地唤醒功能（LWU Enable），且 WAKE 引脚一直为高电平，那么芯片会认为一直有唤醒请求。
  - **结果**：当你命令 TJA1145 进入 Sleep 时，它**可能拒绝进入深度睡眠**，或者进去后**立刻被 WAKE 高电平唤醒**，导致 INH 被拉高，SBC 重新给 MCU 供电，系统无法休眠。
- **解决方案**：如果你确实因为某些原因（比如该引脚耐压高，方便布线）想接上拉，那么软件在进入睡眠前，**必须通过 SPI 把 Local Wake-up 检测功能彻底禁用**，让 TJA1145 忽略 WAKE 引脚的电平。

**结论**：**推荐固定下拉。** 如果接上拉，硬件上不坏，但软件必须记得关掉本地唤醒检测，否则系统无法正常休眠。



## 5 架构对比：KL15 接哪里更合理？

在真实的 ECU 设计中，**把 KL15 同时给 35584 和 TJA1145（或者只给 35584）都是可行的**，但逻辑上有些许区别：

#### 方案一：KL15 只接 35584（TJA1145 WAKE 下拉）

- **唤醒路径**：拧钥匙 -> 35584 被硬线唤醒 -> 35584 直接给 MCU 和 TJA1145 供电。
- **优点**：路径短，即使 CAN 收发器坏了，或者 TJA1145 死机了，只要 35584 是好的，MCU 就能被唤醒（这对于诊断或安全功能很重要）。
- **TJA1145 状态**：TJA1145 此时是被动上电（VCC 来电了），它不需要依靠 WAKE 引脚，也不需要拉高 INH。

#### 方案二：KL15 接 TJA1145 的 WAKE（TJA1145 INH 接 35584 WAK）

- **唤醒路径**：拧钥匙 -> TJA1145 检测到 WAKE 高电平 -> TJA1145 拉高 INH -> 35584 被 INH 唤醒 -> 供电。
- **优点**：TJA1145 可以在硬件层面记录“这次醒来是因为 KL15”，MCU 醒来后读 SPI 寄存器就能区分“点火唤醒”和“CAN 唤醒”。
- **缺点**：唤醒路径依赖 TJA1145。如果 TJA1145 损坏，或者 SPI 配置把 WAKE 引脚禁用了，即使拧了钥匙，MCU 也起不来。这在某些安全等级要求高的 ECU 上是不被允许的。

#### 总结建议

针对“如果不接 KL15，直接硬件下拉或上拉会不会有问题”：

1. **接下拉（GND）**：**完全没问题，放心用。** 这是标准做法，只要 TJA1145 的 VCC 脚由 SBC 供电即可。
2. **接上拉（VBAT/VCC）**：**电气上没问题，但逻辑上是个坑。** 必须在软件配置里**关闭 Local Wake-up 功能**，否则会导致系统无法进入休眠或反复重启。

**工程建议**：在量产硬件设计中，即使你现在不用 KL15 唤醒 TJA1145，**也建议在 WAKE 引脚和 KL15 之间预留一个 0 欧电阻或二极管的位置**，并保留一个下拉电阻的位置。这样，如果以后发现需要通过 TJA1145 区分 KL15 唤醒源，硬件不用改版，只需要调整焊接即可。

## 6 假设项目只需要kl15唤醒，那kl15直接接到电源芯片的唤醒引脚不就好了，把1145的INH引脚下拉掉

**在“仅需 KL15 硬线唤醒”的项目中，TJA1145 的 INH 引脚完全可以不接电源芯片，直接下拉处理，整个系统也能正常工作。**

**INH 是否必须接电源芯片，取决于 TJA1145 是否承担唤醒任务。**

- **承担任务（支持 CAN 远程唤醒）**：INH 必须接 35584，否则无法把系统从无电状态拉起来。
- **不承担任务（仅 KL15 本地唤醒）**：INH 就是个多余的高压输出脚，直接下拉或悬空（按手册建议）即可。此时 TJA1145 就是一颗**带 SPI 诊断功能的普通 CAN 收发器**，和 TJA1043 在单纯通信场景下的用法差不多。

### 6.1 为什么可以不用 INH？

TJA1145 的 INH 引脚存在的唯一目的，就是**在芯片没有 VCC 供电（即 SBC 休眠）时，依靠 VBAT 常电，通过拉高 INH 去“指挥”电源芯片给系统上电**。

如果项目的唤醒源只有 KL15：

- **KL15 直接接 35584**：拧钥匙 -> 35584 直接被硬线叫醒 -> 35584 开始输出 VCC。
- **TJA1145 的角色变了**：它不再负责“唤醒系统”，而是变成了一个**纯粹的被供电设备**。VCC 来了它就工作，VCC 没了它就睡觉。
- **既然 TJA1145 不需要主动去叫醒谁，INH 引脚自然就失去了作用。** 一颗不用的输出引脚，直接做下拉（或悬空，视芯片手册要求，通常建议下拉）终结即可。

### 6.2 系统上电时序会变成什么样？

在纯 KL15 方案下，时序变得非常简单粗暴：

1. **初始**：整车休眠，35584 关闭，VCC=0，MCU 没电，TJA1145 也没电（但 VBAT 有常电供着内部低功耗监听电路，如果 CAN 唤醒没关，它其实还在“偷听”总线，但偷听到了也起不了作用，因为 INH 没接）。
2. **点火**：KL15 拉高 -> 35584 的 WAK/EN 引脚收到高电平。
3. **供电**：35584 打开，VCC 输出 5V/3.3V。
4. **启动**：MCU 上电复位，TJA1145 的 VCC 上电。
5. **初始化**：MCU 跑代码，通过 SPI 把 TJA1145 配置为 Normal 模式，开始正常的 CAN 通信。

### 6.3 需要注意的“坑”（工程细节）

虽然逻辑成立，但在硬件设计和软件配置上，有几个点必须处理好，否则会有隐患：

#### 坑 1：TJA1145 的“惯性”唤醒（CAN 误唤醒导致漏电）

- **现象**：虽然你 INH 没接 35584，但如果 TJA1145 的 CAN 唤醒功能（CWE）没关，当总线上有垃圾报文时，TJA1145 内部检测到总线活动，**它依然会尝试把 INH 拉高**（只不过这个高电平没接到 SBC，所以 35584 不会上电，MCU 不会醒）。
- **后果**：INH 引脚在做无用功，同时 TJA1145 内部的唤醒标志位被置位，芯片内部状态变了。
- **影响**：下次 KL15 唤醒 MCU 后，MCU 读 TJA1145 状态寄存器时，可能会误以为“上次系统醒来是因为 CAN 唤醒”，导致软件逻辑判断出错。
- **对策**：MCU 在每次休眠前（关闭 35584 之前），或者每次启动初始化时，通过 SPI **清除 TJA1145 的唤醒标志，并且最好直接禁用 CAN 唤醒功能**。

#### 坑 2：进入休眠时的时序

- 当你关闭 KL15 时，35584 断电，VCC 消失。TJA1145 会瞬间掉电。
- 这通常没问题，因为 TJA1145 允许 VCC 直接掉电（回到 Standby/Sleep 状态）。
- 但为了保护 TJA1145 的内部逻辑，最好在 MCU 检测到 KL15 关闭后，先通过 SPI 给 TJA1145 发送一个 **Go to Sleep 命令**，把模式切到 Sleep，再让 35584 断电。这样下一次上电时，TJA1145 的状态是明确的。

#### 坑 3：KL15 的抗扰与分压

- KL15 是整车级别的硬线，上面会有各种干扰脉冲（抛负载、负脉冲等）。
- 接 35584 的唤醒引脚时，需要做合适的**分压、限流、TVS 保护和 RC 滤波**，确保 35584 不会被误触发或损坏。

## 7 mcu如何识别唤醒源呢？假设项目同时支持kl15、特定帧应用报文、nm报文三种唤醒。硬件上如何连接，才能保证软件能读到真正的唤醒源是谁

### 7.1 硬件连接方案

为了能让 MCU 区分三种唤醒源，硬件的核心原则是：**让不同的唤醒源在硬件上留下不同的“痕迹”，且 MCU 醒来后能够通过 GPIO 或 SPI 读取到这些痕迹。**

推荐方案：唤醒源分流 + 状态寄存器 + GPIO 直连。

1. **KL15 vs CAN 唤醒**：靠 **GPIO 直读 KL15 电平** 或 **TJA1145.WAKE 引脚状态** 区分，硬件层面就能解决。
2. **特定帧 vs NM 报文**：**硬件无法区分**，必须靠 MCU 在 **Listen-Only 模式下被动接收第一帧报文** 来判断。这是 AUTOSAR CanNm 和 CanIf 的标准做法。
3. **硬件设计核心**：**KL15 分压后直连 MCU GPIO** + **TJA1145 和 35584 都保留 SPI/中断接口**，这样 MCU 醒来后能最快、最准地完成唤醒源识别。

| 信号                       | 连接方式                                                  | 作用                                                         |
| -------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| KL15                       | 同时接到 **35584.WAK** 和 **TJA1145.WAKE**（或只接35584） | 让两处都能留下 KL15 的“指纹”                                 |
| 35584.INT                  | 接到 **TC377 的 GPIO**（带中断功能）                      | MCU 醒来后快速查询 35584 的唤醒源                            |
| TJA1145.SPI                | 接到 TC377 的 SPI                                         | MCU 通过 SPI 读取 TJA1145 的事件寄存器，获取 CAN 唤醒标志    |
| TJA1145.INH                | 接到 35584.WAK（**可选但推荐**）                          | 让 TJA1145 也能唤醒 35584，同时 35584 能记录“被 INH 唤醒”这一事件 |
| KL15 分压后直连 TC377.GPIO | 通过分压电阻 + 二极管接到一个 GPIO                        | **最直接的 KL15 状态读取**，MCU 醒来后第一眼就能看到 KL15 是高还是低 |

### 7.2 三种唤醒源的“痕迹”矩阵

MCU 醒来后，通过读取不同的硬件状态，可以构建一个**唤醒源判定矩阵**：

| 唤醒源             | 35584.WAK 是否被触发 | TJA1145.WAKE 是否被触发 | TJA1145.CAN唤醒标志 | KL15 GPIO 电平 |
| ------------------ | -------------------- | ----------------------- | ------------------- | -------------- |
| **KL15 硬线**      | ✅                    | ✅（如果接了）           | ❌                   | **高**         |
| **特定帧应用报文** | ✅（被 INH 唤醒）     | ❌                       | ✅（标准WUP触发）    | 低             |
| **NM 报文**        | ✅（被 INH 唤醒）     | ❌                       | ✅（标准WUP触发）    | 低             |

**关键洞察**：

- **KL15 vs CAN 唤醒**：通过 KL15 GPIO 电平或 TJA1145.WAKE 标志就能直接区分。
- **特定帧 vs NM 报文**：**硬件上无法直接区分！** 因为两者都是 CAN 总线活动触发的。区分这两者必须依靠 **MCU 软件层面的唤醒验证（Wakeup Validation）**。

### 7.3 软件识别唤醒源的完整流程

#### 第 1 步：MCU 上电，进入 Startup

MCU 从复位向量开始执行，EcuM_Init 被调用。

#### 第 2 步：快速读取硬件“痕迹”（在 CAN 初始化之前）

MCU 在 **EcuM_Init 或 EcuM_StartWakeupValidation** 阶段，**立即执行以下动作**（此时 CAN 控制器还未完全打开，总线还没有任何发送行为）：

```c
/* 1. 读取 KL15 GPIO（最快、最直接） */
boolean kl15Active = Dio_ReadChannel(KL15_GPIO_CHANNEL);

/* 2. 通过 SPI 读取 TJA1145 的事件寄存器 */
uint8 tja1145_event = CanTrcv_ReadEventStatus(&tja1145_cfg);
boolean canWakeupFlag = (tja1145_event & TJA1145_EVENT_CAN_WAKEUP) ? TRUE : FALSE;
boolean localWakeupFlag = (tja1145_event & TJA1145_EVENT_LOCAL_WAKEUP) ? TRUE : FALSE;

/* 3. 读取 35584 的中断/状态寄存器（可选） */
uint8 sbc_status = Sbc_ReadStatus(&sbc_cfg);
boolean sbcWakPinTriggered = (sbc_status & SBC_STATUS_WAK) ? TRUE : FALSE;
```

#### 第 3 步：初步判定唤醒源类别

```c
if (kl15Active || localWakeupFlag) {
    // 唤醒源 = KL15 硬线
    wakeupSource = WAKEUP_KL15;
    // 走 KL15 唤醒流程：直接进入正常通信，不需要 CAN 唤醒验证
    EcuM_SetWakeupSource(WAKEUP_KL15);
} else if (canWakeupFlag) {
    // 唤醒源 = CAN 总线（可能是特定帧，也可能是 NM 报文）
    wakeupSource = WAKEUP_CAN;
    // 进入 CAN 唤醒验证流程
    EcuM_SetWakeupSource(WAKEUP_CAN);
    // 启动 CanNm 的被动监听模式，开始验证
} else {
    // 未知唤醒源，可能是干扰，直接进入休眠准备
    wakeupSource = WAKEUP_UNKNOWN;
}
```

#### 第 4 步：CAN 唤醒的进一步验证（区分特定帧 vs NM 报文）

如果是 CAN 唤醒，MCU **进入静默监听模式**（CAN 控制器配置为 Listen-Only，不发送任何报文，不发送 ACK）：

```c
// 配置 MCMCAN 为 Listen-Only 模式
CanIf_SetControllerMode(CANIF_CTRL_MODE_LOM);

// 启动一个验证定时器
EcuM_StartWakeupValidationTimer(CAN_WAKEUP_VALIDATION_TIMEOUT);
```

**验证逻辑**：

- **接收第一帧报文**：MCU 被动接收 CAN 总线上到达的报文。
- **判断报文类型**：
  - 如果收到的第一帧是 **NM 报文**（ID 匹配 CanNm 配置的 NM Tx/Rx ID），则 `wakeupSource = WAKEUP_CAN_NM`。
  - 如果收到的第一帧是 **特定应用唤醒帧**（ID/Data 匹配应用层定义的唤醒帧，比如诊断唤醒帧 0x7DF），则 `wakeupSource = WAKEUP_CAN_APP`。
  - 如果收到的第一帧都不是，继续等待。
- **超时处理**：
  - 如果在超时时间内收到了合法的唤醒帧（NM 或 APP），验证通过，ECU 进入正常通信模式。
  - 如果超时未收到合法帧，验证失败，ECU 进入休眠准备流程。

### 7.4 更精确的硬件方案：让 KL15 直接能被 MCU 看到

为了让 KL15 唤醒源的识别**最快、最可靠**，硬件设计上通常会做以下处理：KL15 分压后直连 TC377 的 GPIO

```
KL15 (12V) ----/\/\/\----+----/\/\/\---- GND
              R1=47k     |
                         +----> TC377.GPIO (例如 P02.0)
                         |
                        ---  C=100nF (去抖)
                        ---
                         |
                        GND
```

- **为什么这样做**：MCU 上电后，**无需等待 SPI 通信完成**，只需读一个 GPIO 电平就能立即知道 KL15 是否有效。这比读 TJA1145 或 35584 的寄存器快得多。
- **工程细节**：需要加 TVS 管保护，防止 KL15 上的负脉冲或抛负载损坏 MCU 引脚。

## 8 在can唤醒源识别上有没有这样一种可能：项目同时支持应用报文特定帧和网络管理报文唤醒，某次真实的唤醒源其实是应用报文特定帧或网络管理报文中的一种，但由于要等到mcu被唤醒后去判定收到的第一帧报文，这就可能存在先后时序差，可能导致误判。例如原本是被nm报文唤醒，但唤醒后canrx收到的首帧却是应用报文特定帧，反之亦然。

这个问题的本质是：**唤醒事件（硬件层面）与 MCU 开始监听（软件层面）之间存在时间窗口，而总线上的报文是持续流动的，所以 MCU 听到的“第一帧”不一定就是触发硬件唤醒的那一帧。**

### 8.1 这个误判的后果是什么？

取决于软件架构对唤醒源的**差异化处理**：

#### 后果 A：如果两种唤醒源最终都导向同一个结果

- **影响很小**。例如：不管是被 NM 唤醒还是应用帧唤醒，最终都是 ComM 打开通信，CanNm 进入 Network Mode，ECU 加入总线。此时误判只是记录了一个错误的“唤醒源标记”，对功能没影响。

#### 后果 B：如果两种唤醒源后续行为不同

- **影响很大**。例如：
  - **NM 唤醒**：ECU 应该参与网络管理，发送 NM 报文，保持唤醒直到总线睡眠。
  - **应用帧唤醒**：ECU 可能只需要响应一次诊断请求，完成后立刻重新休眠，不参与 NM。
- **误判后果**：
  - 实际是 NM 唤醒，但被误判为 APP 唤醒 -> ECU 响应完应用请求后过早休眠，导致网络管理不同步。
  - 实际是 APP 唤醒，但被误判为 NM 唤醒 -> ECU 错误地进入 Network Mode，发送 NM 报文，干扰总线睡眠。

### 8.2 工程上的解决方案

#### 方案 1：唤醒验证窗口 + 持续监听（AUTOSAR 标准做法）

**核心思想**：不纠结“第一帧”是什么，而是**在一个时间窗口内持续监听，只要窗口内出现过合法的唤醒帧（NM 或 APP），就判定为对应唤醒源**。


```c
// 伪代码
EcuM_StartWakeupValidation(CAN_WAKEUP_VALIDATION_TIMEOUT_MS); // 比如 200ms

while (validationTimerNotExpired) {
    frame = CanIf_ReadRxFrame();
    
    if (IsNmFrame(frame)) {
        wakeupSource = WAKEUP_CAN_NM;
        // 不立即退出，继续监听，看是否也有 APP 帧
        nmFrameSeen = TRUE;
    }
    
    if (IsAppWakeupFrame(frame)) {
        appFrameSeen = TRUE;
    }
}

// 验证窗口结束后判定
if (nmFrameSeen && !appFrameSeen) {
    wakeupSource = WAKEUP_CAN_NM;
} else if (!nmFrameSeen && appFrameSeen) {
    wakeupSource = WAKEUP_CAN_APP;
} else if (nmFrameSeen && appFrameSeen) {
    // 两者都看到了，按优先级判定
    wakeupSource = ResolveAmbiguity();
} else {
    // 都没看到，虚假唤醒
    wakeupSource = WAKEUP_UNKNOWN;
}
```


**优点**：

- 不依赖“第一帧”的偶然性。
- 符合 AUTOSAR CanNm 的唤醒验证精神。

**缺点**：

- 验证窗口延长了 ECU 的启动时间（但通常可接受，200ms 内）。
- 如果两种帧在窗口内都出现，仍需要优先级仲裁。


#### 方案 2：使用 TJA1145 的 Partial Networking 硬件过滤（最优解）

**核心思想**：让 TJA1145 在**硬件层面**就只响应**一种**特定的唤醒帧（比如只响应 NM 报文），这样 MCU 醒来后**不需要猜测**，因为硬件已经保证了“能把我叫醒的，只有 NM 报文”。

**配置方式**：

- 通过 SPI 向 TJA1145 写入 Partial Networking 唤醒帧配置：
  - 只配置 **NM 报文的 CAN ID** 作为唤醒帧。
  - **不配置** 应用报文的 ID。
- **结果**：
  - CAN 总线上有 APP 报文 -> TJA1145 不拉高 INH -> MCU 不醒。
  - CAN 总线上有 NM 报文 -> TJA1145 拉高 INH -> MCU 醒 -> MCU 直接知道是 NM 唤醒。

**如果项目同时需要 NM 和 APP 两种唤醒**：

- TJA1145 支持最多 **4 组唤醒帧配置**。
- 可以配置两组：
  - 槽位 0：NM 报文 ID。
  - 槽位 1：APP 特定帧 ID。
- **但**：TJA1145 的唤醒事件寄存器**不区分是哪个槽位触发的**。它只会告诉你“CAN 唤醒发生了”，不会告诉你具体是哪个槽位。
- **所以**：即使使用 PN 过滤，MCU 仍然需要做软件层面的“第一帧”判断，**但** PN 过滤排除了所有无关报文，MCU 听到的第一帧**大概率就是触发唤醒的那一帧**，因为只有被配置的合法唤醒帧才能让总线“出声”。



#### 方案 3：依赖 CanNm 状态机 + 节点检测（AUTOSAR 标准路径）

**核心思想**：**放弃区分“到底是什么帧叫醒了我”，转而关注“唤醒后网络管理的状态”。**

在 AUTOSAR 中，唤醒验证的本质不是“找到凶器”，而是“确认我是否应该留在网络里”。


```c
// 唤醒后，直接进入 CanNm 的 Passive Mode（被动模式）
// 被动模式下，ECU 只监听，不发送任何 NM 报文

// 如果收到任何 NM 报文（不管是别人的 NM 还是自己的 NM ID）：
// -> CanNm 判定网络处于活跃状态
// -> 进入 Repeat Message State
// -> 开始发送自己的 NM 报文
// -> 保持唤醒

// 如果只收到应用帧，没收到 NM 报文：
// -> CanNm 判定网络不活跃
// -> 通知 EcuM：验证失败
// -> ECU 重新休眠
```



**对“第一帧”的态度**：

- **不关心**。只要在验证窗口内看到 NM 报文，就认为是 NM 唤醒；看到 APP 帧而没看到 NM 帧，就认为是 APP 唤醒。
- 如果**两者都看到**，AUTOSAR 通常以 **NM 优先级更高** 处理，因为网络管理的目标是“大家一起醒，大家一起睡”，收到 NM 意味着有人在请求网络活跃。


### 8.3 你提出的“误判”场景的具体应对

#### 场景：实际是 NM 唤醒，但 MCU 听到的第一帧是 APP 帧

| 方案                       | 结果                                                         |
| :------------------------- | :----------------------------------------------------------- |
| **方案 1（验证窗口）**     | 继续听，窗口内一定会收到 NM 报文（因为唤醒源还在发），最终正确判定为 NM 唤醒 |
| **方案 2（PN 过滤）**      | 如果 PN 配置了 NM ID，APP 帧**根本无法触发硬件唤醒**，所以不会出现“醒了后听到 APP 帧”的情况（除非 APP 帧和 NM 帧恰好同时上总线） |
| **方案 3（CanNm 状态机）** | MCU 先看到 APP 帧，暂时认为可能是 APP 唤醒；但随后 NM 帧到达，CanNm 收到 NM 报文，进入 Network Mode，最终行为正确（保持唤醒、参与 NM） |

#### 场景：实际是 APP 唤醒，但 MCU 听到的第一帧是 NM 帧

| 方案                       | 结果                                                         |
| :------------------------- | :----------------------------------------------------------- |
| **方案 1（验证窗口）**     | 继续听，窗口内会收到 APP 帧，正确判定为 APP 唤醒             |
| **方案 2（PN 过滤）**      | 如果 PN 同时配置了 NM 和 APP 两个槽位，MCU 醒来后仍要区分，但此时总线上的报文只有 NM 和 APP（其他报文被过滤掉了），误判概率极低 |
| **方案 3（CanNm 状态机）** | MCU 看到 NM 帧，进入 Network Mode，**实际上“过度唤醒”了**（本可以响应完 APP 就睡，但现在被 NM 拖住了）。这是 AUTOSAR 可接受的保守行为，因为收到 NM 意味着网络活跃，ECU 保持唤醒是安全的 |


### 8.4 最终工程建议

对于你的项目（同时支持 KL15、APP 特定帧、NM 报文三种唤醒源）：

1. **KL15 唤醒**：硬件 GPIO 直读，**不存在竞态**。
2. **CAN 唤醒（APP 帧 vs NM 报文）**：
   - **最优方案**：使用 TJA1145 的 **Partial Networking**，将唤醒帧配置为 **NM 报文 ID**（以及 APP 帧 ID，如果需要），在硬件层面屏蔽无关报文。
   - **软件层面**：采用 **验证窗口 + CanNm 状态机** 的组合：
     - 醒来后进入 Listen-Only。
     - 开启 200ms 验证窗口。
     - 持续监听，记录窗口内看到的所有合法帧。
     - 如果看到 NM 帧 -> 按 NM 唤醒处理。
     - 如果只看到 APP 帧 -> 按 APP 唤醒处理。
     - 如果都没看到 -> 虚假唤醒，回睡。
   - **仲裁策略**：如果窗口内 **NM 和 APP 都出现**，**优先按 NM 唤醒处理**（因为 NM 的语义是“网络需要活跃”，保持唤醒是安全侧行为）。

这样，你提出的“时序差导致误判”的问题，在实际工程中就被**验证窗口 + 硬件过滤 + 保守仲裁**三重机制兜底了。

## 9 总结下各个唤醒源在不同方案下排列组合的关键pin脚连接关系：1、kl15；2、其他硬线信号（例如cc、cp、epb等）；3、任意can报文；4、nm报文；5、特定app报文。指定一套平台化的硬件连接，确保所有方案都能兼容，无论是单个还是多个唤醒源

核心思路是：**“MCU 直连硬线看状态，SBC 汇聚硬线保供电，收发器过滤 CAN 管网络。”**

- **保底**：任何硬线（KL15/CC/CP/EPB等）都能直接打开 35584 供电。
- **过滤**：任何 CAN 唤醒（任意/NM/APP）都先经过 TJA1145，由 TJA1145 决定是否打开 35584。
- **识别**：MCU 醒来后，看一眼 GPIO（KL15 状态），再读两路 SPI（35584 和 TJA1145 的状态），就能 100% 确定是谁叫醒的，完美解决多唤醒源的兼容性问题。

### 9.1 针对各个唤醒源的平台化接线细则

| 唤醒源                      | 平台化接线策略                                               | 作用与备注                                                   |
| :-------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **KL15**                    | 1. 通过分压/滤波接 **35584.WAK** 2. 通过二极管/分压接 **TJA1145.WAKE** 3. 通过分压接 **MCU.GPIO_A** | 1. 主唤醒路径，确保 35584 能醒。 2. 让 TJA1145 也感知到硬线唤醒，复位后 MCU 可读 TJA1145 状态。 3. **MCU 用于快速判定唤醒源**，无需等 SPI。 |
| **其他硬线 (CC/CP/EPB等)**  | 1. 信号调理后接 **MCU.ADC/GPIO**（功能需要） 2. 通过二极管接 **35584.WAK**（或 INT） 3. （可选）接 **TJA1145.WAKE** | 1. MCU 需要处理这些信号的功能。 2. 若该硬线需要唤醒 ECU，则必须汇聚到 35584 的唤醒输入。 |
| **任意 CAN 报文**           | 接 **TJA1145**，使能标准 WUP。 **INH 接 35584.WAK**          | 总线一有动静，TJA1145 拉高 INH，系统上电。**软件必须做虚假唤醒抑制。** |
| **NM 报文 / 特定 APP 报文** | 接 **TJA1145**，启用 **Partial Networking (PN)**。 **INH 接 35584.WAK** MCU 通过 SPI 配置 PN 寄存器 | TJA1145 提前配置好唤醒帧的 ID/Mask/Data。 总线上只有匹配的帧才能拉高 INH。 **注意：必须保留 MCU 的 SPI 通路用于配置和清除标志。** |

------

### 9.2 软件配置与硬件连接的匹配（关键点）

只把线接好是不够的。采用这套平台化硬件，软件必须遵循以下逻辑来保证兼容性：

1. **TJA1145 的 WAKE 引脚**：
   - 既然 KL15 和/或其他硬线接进来了，TJA1145 内部必须**使能 Local Wake-up 检测**。
   - MCU 醒来后，通过 SPI 读 TJA1145 事件寄存器，可以判断是否有本地硬线唤醒发生。
2. **TJA1145 的 PN 功能**：
   - 如果项目支持“NM 唤醒”或“特定 APP 唤醒”，MCU 休眠前必须通过 SPI 写入 **WUFC/WUID/WUDS 寄存器**（配置过滤规则）。
   - 如果项目仅支持“任意 CAN 唤醒”，则关闭 PN，仅使能标准 WUP。
3. **MCU 的 GPIO_A（KL15 直连）**：
   - 这是**区分 KL15 唤醒和其他唤醒源的最快手段**。
   - 在 `EcuM_Init` 的第一时间读这个脚。如果为高，直接判定为 KL15 唤醒，跳过复杂的 SPI 读取流程。
4. **TLF35584 的 INT 引脚**：
   - 35584 的 INT 可以配置为在发生各种事件（过流、唤醒、看门狗超时）时拉低。
   - MCU 醒来后读 35584 的 SPI 状态寄存器，可以确认 35584 当时是因为哪个引脚（WAK/ENA）被叫醒的，从而辅助判断是硬线还是 TJA1145 的 INH。

## 10 从外部总线报文发出，到ecu唤醒，通信栈开始通信整个硬件和软件链路都梳理清楚，尤其是关系到mcu启动和autosar以及最终os跑起来，毫秒任务和中断运行整个链路。从nm唤醒和没有网络管理需求的两种方案，求同存异，说清楚相同点和差异点

从总线报文出现到 OS 拉起 ms 任务，**“硬件上电 -> MCU 复位 -> 底层初始化 -> 静默验证 -> 切 Normal -> StartOS”** 这条主干道是完全相同的。

**核心分歧点出现在验证通过后的“通信栈行为”**：

- **有 NM**：必须跑 CanNm 状态机，先发 NM 报文，参与网络协同休眠。
- **无 NM**：直接由应用接管，发应用报文，自己管自己的休眠。

平台化设计的关键在于：**硬件上把 TJA1145 的 INH 接死到 35584，把 KL15 和 WAKE 接好，预留 SPI。** 这样，无论软件怎么配（开不开 CanNm，开不开 PN），硬件都能无缝兼容。

### 10.1 共同链路：从总线电平到 OS 启动

无论是 NM 唤醒还是非 NM 唤醒，只要是由 CAN 总线活动触发的，前期的硬件和 MCU 启动流程是完全一致的。

#### 10.1.1 硬件唤醒阶段（时间轴：T0 微秒级）

- **总线动作**：外部 ECU 在 CAN 总线上发送报文（显性/隐性交替）。
- **TJA1145 动作**：
  - 低功耗接收器检测到有效唤醒模式（WUP）或匹配的 PN 帧。
  - 内部 VBAT 开关打开，**INH 拉高（12V）**。
- **TLF35584 动作**：
  - WAK 引脚检测到高电平。
  - 内部上电时序启动，**VCC 输出 5V/3.3V** 给 TC377 和 TJA1145 的 VCC。

#### 10.1.2 MCU 启动与 C 环境准备（时间轴：T1 毫秒级）

- **TC377 上电复位**：
  - POR（上电复位）释放。
  - Boot ROM 执行 SSW（Startup Software），检查 BMHD。
  - 跳转用户启动代码 `_START`。
- **C 运行时初始化**：
  - 初始化堆栈指针、CSA。
  - 复制 `.data` 到 RAM，清零 `.bss`。
  - 调用 `main()`。

#### 10.1.3 AUTOSAR 基础层初始化（时间轴：T2 几毫秒内）

- **EcuM_Init**：ECU 状态管理器初始化。
- **Mcu_Init**：配置 MCU 时钟、PLL、RAM 等待状态。
- **Port_Init / Dio_Init**：配置引脚复用。
- **Spi_Init**：初始化 SPI 总线（用于和 TJA1145/35584 通信）。
- **CanTrcv_Init**：**关键步骤**，通过 SPI 把 TJA1145 从 Standby 切到 Normal 模式。
- **CanIf_Init / Can_Init**：**先不启动通信**，配置 CAN 控制器为 **Listen-Only（静默模式）**。

#### 10.1.4 唤醒源验证（时间轴：T3 验证窗口期）

- **EcuM_StartWakeupValidation**：启动验证定时器（如 100ms~200ms）。
- **被动监听**：CAN 控制器开始接收总线数据，但**不发送 ACK，不发送任何报文**。
- **软件判定**：
  - 读 TJA1145 事件寄存器，确认是 CAN 唤醒。
  - 检查收到的报文内容。

#### 10.1.5 通信启动与 OS 启动（时间轴：T4 验证通过后）

- **ComM 放权**：EcuM 调用 `ComM_Nm_NetworkMode`（或直接请求 Full Communication）。
- **CAN 切 Normal**：`CanIf_SetControllerMode(CANIF_CTRL_MODE_NORMAL)`。
- **启动 OS**：`EcuM_StartOS()` -> `StartOS()`。
- **OS 运行**：
  - 初始化完成，进入第一个调度点。
  - 启动 **毫秒任务**（如 `Task_1ms`，由 OS Counter 触发）。
  - 启动 **CAN 接收中断**（`Can_Isr`），收到的报文通过中断/轮询进入 COM 栈。

### 10.2 差异点：NM 唤醒 vs 无网络管理需求

“无网络管理需求”通常指：**ECU 不参与 AUTOSAR 的 CanNm 状态机，可能只需要 KL15 唤醒，或者简单的总线活动唤醒（任意帧）后执行简单逻辑。**

| 维度               | NM 唤醒方案（有 CanNm）                                      | 无网络管理需求方案                                           |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **硬件唤醒配置**   | TJA1145 通常配置为 **Partial Networking**，只响应特定 ID（NM 报文）。 | TJA1145 配置为**标准 WUP**（任意显隐性翻转即可唤醒），或仅依赖 KL15。 |
| **唤醒验证目的**   | 验证收到的**第一帧/窗口内帧是否是合法的 NM 报文**。          | 若仅 KL15，无需验证。 若任意 CAN，验证总线上是否有持续活动，或是否收到特定应用帧。 |
| **CanNm 模块**     | **使能**。验证通过后，CanNm 状态机进入 **Network Mode**。    | **禁用**。CanNm 模块不编译或处于旁路状态。                   |
| **报文发送时机**   | 验证通过后，**首先发送 NM 报文**（Repeat Message State），宣告加入网络。 | 验证通过后，**仅发送应用报文**（如诊断响应或周期数据）。     |
| **休眠逻辑**       | 由 **CanNm 状态机**主导。所有节点不发 NM 后，总线静默，CanNm 超时后请求休眠。 | 由 **EcuM 或应用逻辑**主导。如 KL15 关闭，或应用层命令休眠。 |
| **第一帧误判风险** | 存在。需用验证窗口 + PN 过滤兜底。                           | 若任意帧唤醒，无 NM 需求，误判风险低（因不需要区分 NM/APP）。 |
| **OS 任务差异**    | 需要额外的 **`Task_Nm`**（如 10ms 周期）处理 CanNm 状态机。  | 无 CanNm 任务。仅有应用任务（如 `Task_App`）。               |


### 10.3 详细分链路对比（从总线到 OS）

#### 方案 A：NM 报文唤醒（AUTOSAR 标准网络管理）

1. **外部总线**：ECU_A 的 CanNm 处于 Repeat/Network Mode，周期性发送 NM 报文（如 ID=0x500）。
2. **硬件**：TJA1145 的 PN 滤波器匹配到 ID=0x500，INH 拉高，35584 供电，TC377 启动。
3. **验证**：MCU 进入静默监听。`CanNm_RxIndication` 被调用（内部），确认收到了 NM 报文。
4. **验证通过**：CanNm 进入 **Repeat Message State**。
5. **通信启动**：
   - ComM 请求 Full Communication。
   - CAN 控制器切 Normal。
   - **本 ECU 开始发送自己的 NM 报文**（例如 ID=0x501）。
6. **OS 启动**：
   - `Task_1ms`：基础任务（读取 IO，执行控制逻辑）。
   - `Task_10ms`：**CanNm_MainFunction**，处理 NM 状态机。
   - `Can_Isr`：接收中断，收到 NM/APP 报文。

#### 方案 B：无网络管理（以任意 CAN 报文或特定 APP 帧为例）

1. **外部总线**：ECU_A 发送一帧诊断唤醒请求（如 ID=0x7DF）或任何报文。
2. **硬件**：TJA1145 标准 WUP 检测到总线活动，INH 拉高，系统上电。
3. **验证**：
   - **若仅任意帧**：软件通常不做严格验证，只要总线活动持续即可。
   - **若特定 APP 帧**：静默监听，等待 ID=0x7DF 出现。
4. **验证通过**：
   - 如果收到目标帧，EcuM 通知 ComM 进入通信。
   - **不启动 CanNm**（模块未使能）。
5. **通信启动**：
   - CAN 控制器切 Normal。
   - **本 ECU 不发送 NM 报文**。
   - 根据需要发送应用响应（如诊断响应 0x7E8）。
6. **OS 启动**：
   - `Task_1ms`：基础任务。
   - `Task_App`：应用逻辑任务。
   - `Can_Isr`：接收中断。

### 10.4 软件架构层面的“求同存异”

#### 相同点

- **底层驱动链路完全一致**：`Mcu` -> `Port` -> `Spi` -> `CanTrcv` -> `Can` -> `CanIf` 的初始化顺序不变。
- **唤醒验证的硬件基础一致**：都需要在验证期间保持**静默**，避免误发报文。
- **OS 启动机制一致**：都是通过 `EcuM_StartOS` 拉起 OS，毫秒任务和中断的机制相同。

#### 差异点

- **CanNm 模块的存在与否**：
  - 有 NM：CanNm 是 **通信栈的“核心调度者”**，ComM 向 CanNm 请求通信，CanNm 决定何时发 NM、何时休眠。
  - 无 NM：ComM 直接控制 CanIf 和 Can，应用层直接请求通信。
- **休眠时序**：
  - 有 NM：休眠由 **CanNm 的 Bus-off/Silent 超时** 触发，保证所有节点同步休眠。
  - 无 NM：休眠由 **KL15 掉电** 或 **应用层自己计时** 触发，不考虑网络同步。
- **唤醒源识别精度**：
  - 有 NM：强烈建议用 **PN 功能**，硬件直接过滤出 NM 帧，避免被无关 APP 帧吵醒。
  - 无 NM：一般不需要 PN，标准 WUP 即可（即使被无关帧吵醒，因为逻辑简单，重新睡下即可）。
