# Q&A

Architecture: Infineon TC377 + TLF35584 + TJA1145

## 1
### Q&A

* Q: 单板第一次12V上电时，没有唤醒信号，此时35584应该都在未初始化或休眠态，1145、377应该都处于未上电状态，因为sbc还没有对外输出3.3v或5v供电。sbc收到外部的硬线信号被唤醒，或通过can唤醒1145来间接唤醒sbc，这两种方式让sbc进入工作态并对外输出供电。此时377进入初始化流程。但是不是有个矛盾点：1145还没有经sbc供电，它收到can唤醒信号后，如何通过inh引脚对外输出，来唤醒sbc呢？

* A: TJA1145 在设计上就是为了解决“系统主电源断电时如何被总线唤醒”这个问题的。它的秘诀依然在于**双电源架构**。

### 1.1 核心：TJA1145 的“常电”引脚（VBAT）

TJA1145 通常有这几个电源引脚：

- **VBAT**：**电池常电引脚**。在硬件设计时，这个引脚**直接连接 12V 蓄电池**，不经过 35584（SBC）的控制。
- **VCC**：**逻辑供电引脚**。这个引脚接 35584 输出的 5V 或 3.3V，用于正常通信。
- **VIO**：数字接口电平参考（接 MCU 的 IO 电平）。

**关键机制**：只要 12V 蓄电池还连着 ECU，**VBAT 引脚就始终有电**。此时，即使 VCC 完全没有电（即 35584 处于休眠、未对外输出），TJA1145 内部的一个**极低功耗的“总线唤醒接收器”**依然处于待命状态。

### 1.2 解决矛盾：没有 VCC，INH 怎么输出高电平？

你可能会疑惑：芯片主逻辑没供电（VCC=0），它怎么有力气把 INH 拉高呢？

**答案**：TJA1145 的 INH 引脚是**高压引脚**，它的驱动能量直接来源于 **VBAT（12V 常电）**，而不是 VCC。

TJA1145 数据手册中关于 INH 的描述明确指出：**INH 引脚是一个高压输出引脚，内部通过一个高边开关连接到 VBAT**。

唤醒流程如下：

1. **监听**：TJA1145 由 VBAT 供电的微弱监听电路一直在线。
2. **识别**：CAN 总线上出现符合 ISO 11898 标准的唤醒报文（Wake-up Pattern）。
3. **动作**：TJA1145 内部逻辑被触发，**打开 VBAT 到 INH 的开关**。
4. **输出**：INH 引脚直接输出 VBAT 电压（通常是 12V 或电池电压）。
5. **唤醒 SBC**：这个 12V 的 INH 信号传到 35584 的唤醒输入引脚（如 WK 或 EN），35584 被激活，开始输出 3.3V/5V 给 MCU 和 TJA1145 的 VCC。

### 1.3 三种场景的完整状态流转

#### 场景 A：单板第一次接 12V 常电（无任何唤醒信号）

- **状态**：35584 处于**未初始化或休眠态**，不输出 3.3V/5V。
- **TJA1145**：**VCC=0，但 VBAT=12V**。TJA1145 进入 **Standby（待机）或 Sleep（睡眠）模式**（具体模式取决于硬件上电默认配置和软件是否曾经配过）。此时它的 INH 是**悬空或拉低**的（取决于模式，但不会主动输出高电平去打开 35584）。
- **结果**：MCU（377）和驱动芯片没电，单板处于静默状态，只有极低的静态电流（TJA1145 监听 + SBC 休眠）。

#### 场景 B：硬线直接唤醒 SBC

- **动作**：外部点火信号（IGN）或硬线信号直接输入到 35584 的唤醒引脚。
- **过程**：35584 被硬线电平触发，**直接**开始上电，输出 3.3V/5V。
- **TJA1145**：VCC 得电，TJA1145 进入正常模式。
- **377**：得电启动。

#### 场景 C：通过 CAN 唤醒 TJA1145，间接唤醒 SBC

- **初始**：单板处于休眠状态（35584 关断，VCC=0），但 12V 常电在线（VBAT=12V）。
- **动作**：外部 ECU 在 CAN 总线上发唤醒报文。
- **过程**：TJA1145 的低功耗接收器检测到唤醒（**注意：此时 35584 仍未工作**） -> TJA1145 的 INH 由 **VBAT 驱动**输出高电平 -> 35584 检测到 INH 高电平 -> 35584 打开主电源 -> 377 启动。

## 2
### Q&A
* Q: 场景C中的Wake-up Pattern需要提前配置在1145里吗？假设需要支持网络管理报文唤醒呢？或是特定帧唤醒？或是任意帧唤醒？1145能配置成同时支持网络管理报文唤醒和特定应用报文帧唤醒吗？要如何配置1145，377是不是也需要在软件里匹配配置？

* A: **Wake-up Pattern（唤醒模式）不需要提前把“具体数据”配置进去，但需要提前通过 SPI 配置 TJA1145 的“唤醒判定规则寄存器”。**

### 2.1 Wake-up Pattern 到底是什么？
在 TJA1145 的硬件机制中，它所谓的“Wake-up Pattern”**不是**指具体的一帧数据（比如 ID=0x123, Data=0xAA），而是指 **CAN 总线上的物理电平特征**。

根据 ISO 11898-6（唤醒规范）和 TJA1145 数据手册，标准的 CAN 唤醒模式（Standard Wake-up Pattern, WUP）定义如下：

- 在总线上监测到一个 **显性（Dominant）电平**（持续至少 $t_{filter}$时间，通常是几百纳秒到几微秒）。
- 随后跟着一个 **隐性（Recessive）电平**（持续至少 $t_{filter}$ 时间）。
- 如此交替出现 **至少 2 次**（具体次数可配置）。

**结论**：只要总线上有任意 CAN 控制器在发送数据（无论是 NM 报文、应用报文还是错误帧），总线上就会出现显性-隐性交替的电平。因此，**硬件唤醒机制本身不区分 ID 或数据内容**。

### 2.2 网络管理报文唤醒、特定帧唤醒、任意帧唤醒
在实际 ECU 开发中，这三种唤醒在软硬件分工上完全不同：

#### 2.2.1 任意帧/任意总线活动唤醒（最简单，功耗较高）
- **TJA1145 配置**：使能 CAN Wake-up 功能（`CWE=1`），配置标准 WUP。
- **现象**：总线上只要有任何风吹草动（哪怕是一个错误帧），TJA1145 就会拉高 INH，唤醒 SBC 和 MCU。
- **优点**：不会漏唤醒。
- **缺点**：总线干扰可能导致 ECU 被频繁误唤醒，不符合低功耗要求。

#### 2.2.2 特定帧唤醒 / 网络管理报文唤醒（进阶，AUTOSAR 标准做法）
**关键点：在绝大多数量产项目中，硬件不负责区分具体报文，只负责“叫醒”，具体区分交给 MCU 软件。**

- **TJA1145 配置**：依然是配置标准的 WUP（显隐性交替）。TJA1145 本身**无法**配置成只响应 ID=0x500 的 NM 报文而忽略 ID=0x123 的应用报文（除非使用 TJA1145 的 Partial Networking 功能，见下文）。

- **工作流程（软硬件结合）**：

  ##### 第 1 步：硬件唤醒，MCU 上电

  - CAN 总线上出现任意报文（可能是 NM，可能是应用报文，甚至是干扰）。
  - TJA1145 检测到总线活动 -> INH 拉高 -> SBC 上电 -> TC377 上电复位。

  ##### 第 2 步：EcuM 确认唤醒源（仅读状态，不碰总线）

  - MCU 开始跑启动代码。
  - EcuM（ECU State Manager）启动，通过 SPI 读取 TJA1145 的事件寄存器。
  - 得出结论：“哦，是 CAN 总线唤醒了我”。
  - 但是，ECU 目前处于 **Startup 状态**，网络状态机是 **COMM_NO_COMMUNICATION**（禁止通信）。

  ##### 第 3 步：进入 CAN 侦听/验证状态（Listening / Passive）

  此时，MCU **打开 CAN 控制器的接收功能，但严格保持发送静默（不发送任何报文）**。

  - **硬件配置**：TC377 的 MCMCAN 控制器被初始化。
    - **收发器（TJA1145）**：通过 SPI 将 TJA1145 从 Standby 模式切换到 **Normal 模式**，但 TJA1145 的 TXD 引脚保持拉高（隐性）。收发器可以接收，但即使 MCU 不发送，总线也不会因为 MCU 而动作（相当于接收器在线）。
    - **CAN 控制器**：MCMCAN 设置为**不发送 ACK（Self Reception / Silent Mode，静默模式）**，或者仅仅开启接收中断，**完全关闭发送 API**。
  - **网络管理（CanNm）动作**：
    - CanNm 进入 **Network Mode 的 Repeat Message State 或立刻进入 Listen 模式**。
    - CanNm 开始**监听总线上的数据**。

  ##### 第 4 步：唤醒验证（Wakeup Validation）

  - CanNm 会设置一个定时器（通常叫 `CanNmTimeoutTime` 或 `CanNmWaitBusSleepTime`）。
  - **情况 A：收到预期报文（如有效的 NM 报文）**
    - CanNm 确认收到合法的 NM 报文（或者应用层指定的特定唤醒帧）。
    - **验证成功**。
    - CanNm 通知 EcuM：“验证通过，请给我供电，我要开始通信了”。
    - EcuM 执行 `ComM_Nm_NetworkMode`，网络状态切换为 `COMM_FULL_COMMUNICATION`。
    - **此时，CAN 控制器才被允许发送 ACK 和发送报文。** ECU 正式加入总线，给外部 ECU 发出“我醒了”的信号。
  - **情况 B：超时未收到合法报文（收到的是干扰或无关应用帧）**
    - CanNm 告知 EcuM：“验证失败，这是虚假唤醒”。
    - EcuM 关闭 CAN 控制器，通过 SPI 把 TJA1145 重新设置为 Sleep 模式。
    - SBC 关闭电源，ECU 重新回到休眠状态。
    - 全程 MCU 没有向外发送过任何错误帧、ACK 或应用报文。

#### 2.2.3 TJA1145 的 Partial Networking（特定帧硬件唤醒）

如果你希望在硬件层面就过滤掉非唤醒帧，TJA1145 系列（特别是 TJA1145A/FD 或 TJA1145B）支持 **Partial Networking（局部网络，ISO 11898-6）**。

- **原理**：TJA1145 内部集成了一个简单的 CAN 协议解析器（不仅看物理电平，还看数据链路层）。
- **配置方式**：通过 SPI，你可以提前向 TJA1145 写入一组 **唤醒帧配置寄存器（WUFC，Wake-up Frame Control）**。
  - 你需要指定 **CAN ID**（例如 NM 报文的 ID=0x500）。
  - 你需要指定 **数据掩码（Data Mask）**（例如只关心 Byte0 的 bit0）。
  - 你需要指定 **数据内容（Data Value）**。
- **效果**：只有总线上出现与你配置的 ID 和 Data 完全匹配的报文时，TJA1145 才会拉高 INH。如果总线上是其他应用报文，TJA1145 保持沉默，SBC 继续睡觉。
- **代价**：配置复杂，需要计算 CRC，且**只能配置有限的几组**（通常是 1 到 4 组唤醒帧）。

### 3. TJA1145 能否同时支持 NM 报文和特定应用报文唤醒？

**如果使用 Partial Networking 功能：**
可以**部分支持**。TJA1145 通常有多组唤醒寄存器（例如支持配置 4 个不同的唤醒 ID）。你可以：

- **槽位 0**：配置成 NM 报文的 ID（如 0x500）。
- **槽位 1**：配置成特定的应用诊断唤醒报文 ID（如 0x7DF）。
- 只要满足其一，即可唤醒。

**如果不使用 Partial Networking（即常规配置）：**
它**同时也支持**所有的报文。因为它工作在物理层，不管是 NM 报文还是应用报文，只要总线有电平翻转它就醒。区别只在于 MCU 醒来后软件是否认账。

### 4. 如何配置 TJA1145？TC377 需要怎么配合？

为了实现在验证阶段的“监听且静默”，TJA1145 和 TC377 的配置如下：

**TJA1145（通过 SPI 配置）：**

1. 唤醒后，MCU 首先读 TJA1145 的事件寄存器，确认是 CAN 唤醒。
2. 将 TJA1145 从 **Standby** 切到 **Normal** 模式。
3. **关键点**：为了监听总线，TJA1145 的接收器是开启的。但此时 TJA1145 的 TXD（发送数据输入）引脚被 MCU 拉高（隐性）。**只要 MCU 不拉低 TXD，TJA1145 就不会驱动总线为显性，也不会发出 ACK**。

**TC377（MCMCAN 配置）：**

1. **初始化阶段**：MCMCAN 设置为 `CAN_CTRL_MODE_LOM`（Listen Only Mode，只听模式）或 `MON`（Monitor）。
2. **在 Listen Only 模式下**：
   - 可以收到总线上的报文。
   - **硬件上自动禁止发送 ACK/错误帧/数据帧**。
3. **验证通过后**：
   - ComM 请求 `CanIf_SetControllerMode(CANTRCV_OPMODE_NORMAL)`。
   - MCMCAN 退出 Listen Only，进入 Normal 模式，此时才能正常发报文和 ACK。

## 3
### Q&A
* Q: 超时未收到合法报文，重新进入休眠，因为此时总线上还有无效报文（非唤醒应用报文帧或非唤醒nm报文），那岂不是立马又会唤醒1145，再次把sbc唤醒，有一次进入判定，然后再次休眠，循环往复，这是可接受的吗？

* A: **这完全不可接受，必须通过软件和硬件机制来打破这个循环。**

### 1. 第一道防线：TJA1145 的“唤醒锁存”机制
TJA1145 内部有一个唤醒事件锁存器。

- **关键特性**：当总线活动触发唤醒后，TJA1145 会**锁存（Latch）**这个唤醒事件，并且**自动关闭/屏蔽后续的唤醒检测**（或者说唤醒标志位被置位后，不会因为总线还在活动而反复触发硬件复位动作）。
- **流程表现**：只要 MCU 还没通过 SPI 去**清除唤醒标志（Clear Wake-up Flag）**，TJA1145 就不会再次因为总线上的无效报文去拉高 INH。
- **问题场景**：MCU 被无效报文唤醒 -> MCU 进入验证 -> 验证失败 -> MCU 下发“进入休眠”命令 -> **在执行休眠命令前，MCU 会先清除 TJA1145 的唤醒标志** -> 然后发送 Sleep 命令。
- **结果**：只有当唤醒标志被清除并进入 Sleep 后，TJA1145 才会重新武装（Re-arm）唤醒检测功能。

### 2. 第二道防线：MCU 软件（EcuM/CanNm）的“休眠屏蔽”策略

如果总线上的无效报文是**持续不断**的（比如总线上其他节点在疯狂发应用报文，或者总线短路导致一直有杂波），MCU 软件不能机械地“验证失败就立刻睡”。

AUTOSAR 网络管理引入了 **Bus-off / 被动等待 / 延后休眠** 的概念：

- **策略 A：提高休眠门槛（Timeout Extension）**
  软件逻辑通常是：验证失败 -> 不睡，继续听一段时间 -> 如果总线一直忙，就一直等 -> 直到**总线安静了**（比如检测到 Bus-Silent 持续 1 秒或更久），软件才认为外部环境安全了，此时才清除 TJA1145 标志并命令休眠。
- **策略 B：软件屏蔽唤醒源**
  如果软件发现“导致我醒来的这个源是个捣蛋鬼”，MCU 可以在本次休眠前，**通过 SPI 修改 TJA1145 的寄存器配置**。
  - 比如：关闭 CAN 总线唤醒（Disable CAN Wake-up），只保留硬线唤醒。
  - 或者：配置成 Partial Networking（局部网络），让 TJA1145 在硬件层面就过滤掉那个“非唤醒应用报文”，只对特定的 NM 报文敏感。
  - 这样，即使总线上还有无效报文，TJA1145 在硬件上就无视它了，不会产生中断，也不会拉高 INH。

### 3. 第三道防线：物理层的“总线静默”假设

在正常的车载网络设计中，**网络管理（NM）的核心逻辑就是“大家一起睡，一起醒”**。

- **正常场景**：所有 ECU 要休眠时，它们会先协调好。最后休眠的 ECU 会停止发送 NM 报文。一旦所有 ECU 都停止发送 NM 报文，**整条 CAN 总线就处于“总线静默（Bus Silent）”状态**（只有纯隐性电平，没有任何报文）。
- **无效报文场景**：如果总线上还有应用报文在飞，说明**还有 ECU 在工作**（比如娱乐系统还在放歌，或者某个节点还没准备睡）。
- **设计策略**：如果你的 ECU 不需要参与当前的通信（比如变速箱不需要娱乐系统的报文），但又因为娱乐系统的报文被吵醒了，**软件通常会选择“陪跑”**。即：既然总线上还有系统在工作，说明整车还没到完全休眠的时候，那变速箱 ECU 索性也保持唤醒（或者进入一个低功耗的“听但不发”状态），**等到总线彻底静默了，再执行休眠**。

### 4. 极端的异常处理：连续唤醒计数

如果发生极端情况（例如总线对地短路导致持续显性，或者某个节点程序跑飞疯狂发错误帧），MCU 软件通常会有一个**计数器**。

- 逻辑：如果我在短时间内（如 10 秒内）被连续唤醒超过了 N 次（如 5 次）。
- 动作：MCU 会判定“硬件可能存在故障”。
- 结果：MCU 可能直接命令 SBC 进入 **Fail-Safe 模式**，或者**彻底关闭 TJA1145 的 CAN 唤醒功能**，只保留硬线（KL15）唤醒，以防止电池电量被耗尽。
